# עוזר לנציגי שירות – ביטול, החזרים ותביעות

## מה זה

נציג מקליד שאלה חופשית ("הלקוח 4471 רוצה לבטל, מה מגיע לו?"), והכלי עונה מתוך נתוני הפוליסה ו-4 מסמכי הנהלים, עם ציטוט מקור לכל עובדה ורשימה מפורשת של מה שחסר. סכומים ותאריכים של לקוח מסוים, והחלטות הסלמה, נקבעים בקוד בלבד. מודל השפה רק מבין את השאלה, וכותב תשובות מצוטטות לשאלות כלליות על הנהלים; תשובה כזו רשאית לציין רק מספרים שמופיעים בנהלים עצמם, והקוד בודק זאת לפני שהתשובה מוצגת. החריג היחיד: מספר פוליסה או לקוח מהשאלה, ורק בהקשר של מזהה ("פוליסה 4471", "לקוח C-1088"); בכל הקשר אחר – וכל מספר שמסומן במטבע (₪, ש"ח, NIS) – המספר חייב להופיע בנהלים.

## הרצה

Python 3.11+.

```bash

source .venv/bin/activate
pip install -r requirements.txt
export ANTHROPIC_API_KEY=...         # אופציונלי – בלעדיו הכלי עובד במצב מילות מפתח בלבד. לעולם לא לעשות לו commit.
export ANTHROPIC_MODEL=...           # אופציונלי, ברירת מחדל claude-haiku-5-5
```

```bash
python -m insurance_assistant.cli "הלקוח 4471 רוצה לבטל, מה מגיע לו?"
python -m insurance_assistant.cli "4425 רוצה לבטל" --no-llm      # בלי מודל שפה
python -m insurance_assistant.cli "4471 רוצה לבטל" --debug       # ה-Decision המלא כ-JSON
```

בדיקות והערכה:

```bash
python -m pytest -q
python -m eval.run_eval [--no-llm] [--md eval/report.md]

```

## ארכיטקטורה

1. מילות מפתח של רגולטור נבדקות בקוד **לפני** כל קריאה למודל (`guardrails.py`); אם הן מופיעות – העברה מיידית למנהל משמרת.
2. מזהים (פוליסה, לקוח, שם, מוצר) מחולצים בקוד בלבד (`extract.py`).
3. כוונה: המודל מסווג (JSON מובנה); אם הוא לא זמין או מחזיר פלט לא תקין – גיבוי של מילות מפתח.
4. זיהוי הלקוח והפוליסה (`assistant.py`): מזהים סותרים, כמה לקוחות או פוליסות אפשריים, מספר שלא נמצא או מוצר שלא תואם – אין תשובה, אלא בקשה להבהרה. שני מספרי פוליסה בשאלה אחת – הנציג נשאל לאיזו פוליסה הלקוח מתכוון, בלי סכומים (הראשון עשוי להיות דווקא זה שהלקוח החריג).
5. בטיחות תביעות: תביעה פתוחה או לא ידועה עם כל רמז לביטול – העברה למנהל משמרת.
6. כללים דטרמיניסטיים עם ציטוט סעיף לכל עובדה (`rules/`), ואז תבנית קבועה.

כל הנתונים עוברים דרך `PolicyRepository` ו-`ValidatedPolicyRepository`: בייצור מחליפים את ה-CSV במימוש מול ה-API בלי לגעת בכללים, ו-`tests/test_repository_swap.py` מוכיח שההחלטות זהות. העיקרון: במצב מודל, מילות המפתח לעולם לא יוצרות כוונה שהמודל לא הציע – הן יכולות רק להסלים, או לאשר כוונה שהמודל כבר מנה.

## מעבר ל-API

`insurance_assistant/api_repository.py` הוא **מתאם לדוגמה לחוזה משוער** – פורמט ה-API האמיתי של מערכת הפוליסות לא ידוע, וזו שאלה פתוחה לרונית. החוזה המשוער:

- `GET {base}/policies/{policy_id}` – 200 עם אובייקט JSON בשמות העמודות של ה-CSV; 404 – הפוליסה לא קיימת.
- `GET {base}/customers/{customer_id}/policies` – 200 עם רשימת אובייקטים כאלה (רשימה ריקה – אין פוליסות).
- טוקן אופציונלי מ-`POLICY_API_TOKEN`, נשלח ככותרת `Authorization: Bearer`. הוא נבדק בעלייה (טוקן עם רווח או תו בקרה נדחה) ולעולם לא מודפס – גם לא בהודעות שגיאה.

```bash
python -m insurance_assistant.cli --source api --api-url http://... "הלקוח 4471 רוצה לבטל, מה מגיע לו?"
```

(או `POLICY_API_URL` במקום `--api-url`). במצב הזה בדיקות ה-CSV בעלייה מדולגות; בדיקות מסמכי הנהלים עדיין רצות.

- **אותם מפענחים כמו ה-CSV:** כל שדה עובר דרך אותם מפענחים, ולכן תאריכים, מספרים ובעיות נתונים מתנהגים זהה. `tests/test_api_repository.py` מריץ שרת API מדומה ומוכיח החלטות זהות ל-CSV.
- **אי-זמינות אינה "לא נמצא":** timeout, שגיאת חיבור, HTTP 5xx, כל סטטוס שאינו 200/404, הפניה (redirect – אף פעם לא מבוצעת, כדי שהטוקן לא יישלח לשרת אחר), כל כשל בבניית הבקשה, בשליחתה או בקריאת התשובה, JSON לא תקין, תשובה במבנה שגוי או רשומה של פוליסה או לקוח אחרים – כולם מחזירים "מערכת הפוליסות לא זמינה כרגע" (`DATA_SOURCE_UNAVAILABLE`), בלי סכומים. רק 404 נחשב "לא נמצא". בדיקת הרגולטור עדיין גוברת.
- **קריאה אחת לכל פוליסה בכל שאלה:** כל פוליסה נקראת פעם אחת, ואותה רשומה משמשת לזיהוי, לבדיקת התביעות, לכללים ולאזהרת הבטיחות. אם שתי קריאות של אותה פוליסה באותה שאלה סותרות – "לא זמין", בלי סכומים. שתי רשומות עם אותו מספר פוליסה מסומנות כסותרות, כמו ב-CSV.
- **מגבלה – אין חיפוש לפי שם:** בחוזה המשוער אין חיפוש טקסט חופשי לפי שם, ולכן שם לקוח בשאלה מזוהה רק מול מקור ה-CSV; מול ה-API צריך מספר פוליסה או מספר לקוח.

- **"לא המציא"** נמדד ברמת התוצאה: מקרים שצפויה בהם תשובה חלקית או סירוב לא חזרו אף פעם כתשובה מלאה.
- **זמני תגובה:** חציון 1.2 שניות, p95 2.4 שניות, מקסימום 5.1 שניות. מקרה אחד מעט מעל יעד ה-5 שניות (`general-calc-with-id`) – שאלה כללית שמבצעת שתי קריאות למודל (כוונה + תשובה). הסלמה בגלל רגולטור לוקחת כ-0 מ"ש (אין קריאה למודל).
- **7 שאלות עוינות עברו**, כולל ניסיון prompt injection שביקש להבטיח ללקוח 5000 ₪ – המספר לא הופיע אף פעם. הפלט המלא של בדיקת היציבות שמור ב-`eval/stability_report.txt` (מספר ההרצות מודפס בקובץ).
- **הערכים הצפויים** ב-`eval/cases.json` חושבו ידנית מתוך הנהלים לפני הבנייה, ואומתו על ידי סוקר עצמאי (מודל של חברה אחרת) – אף פעם לא על ידי הסוכן שכתב את הקוד.
- **`eval/report.md`** הוא הדוח למנהלת – התשובה של רונית ל"איך אדע שהכלי עונה נכון".

**ביקורת עצמאית סופית:** סקירה עצמאית אחרונה (Codex, קריאה בלבד) אישרה את כל 57 הערכים הצפויים שהיו קיימים ו-8 ביטולים שחושבו ידנית, ומצאה 7 בעיות בקלטים חריגים שהשפיעו על כסף או על הסלמה (למשל: מספר טלפון שנקרא כמספר פוליסה, שם משפחה ארוך יותר שהותאם ללקוח קיים, אזכור רגולטור בנטייה שלא זוהה, וסכום שהועתק מהשאלה והתקבל בתשובה כללית), 2 בעיות עמידות ו-2 טענות מוגזמות בתיעוד. הבעיות שנמצאו בסקירה הראשונה תוקנו, ו-6 מקרי רגרסיה נוספו להערכה. בדיקה ממוקדת חוזרת מצאה ניסוחים נוספים של אותם סוגי בעיות (סכומים במטבע, אותיות שימוש, שמות, מוצרים), והם תוקנו ברמת הכלל ולא רק לניסוח שדווח, עם 5 מקרי רגרסיה נוספים. פענוח טקסט חופשי במצב מילות מפתח נשאר היוריסטי (ראו מגבלות).

## מה לא עובד / מגבלות

- **מצב מילות מפתח בלבד** (אין מפתח, או שהמודל נכשל): מושא הביטול מזוהה באופן היוריסטי עם רשימת החרגות; ניסוחים כמו "לבטל רק את הוראת הקבע" או "לבטל את הרשאת החיוב בכרטיס" עדיין עלולים להיקרא כביטול פוליסה – מצב המודל מטפל בהם. מילים נרדפות לביטול (לסגור, לעזוב…) ושאלות כלליות לא מובנות. בפוליסה עם תביעה פתוחה הנציג עדיין מקבל אזהרת תביעה פתוחה, וכשמודל מוגדר נכשל מוצג באנר "מצב מוגבל".
- **הסלמת יתר מכוונת:** המילה "מפקח" לבדה (למשל "מפקח בנייה"), דגל הרגולטור של המודל, ובמצב מילות מפתח – שלילות מורכבות או "אחרי/דמי ביטול" בפוליסה עם תביעה פתוחה. הסלמה שהוחמצה היא תלונה לרגולטור; הסלמה מיותרת עולה למנהל דקה.
- **"אלא" אחרי ביטול שלילי:** כש"אלא" מופיע אחרי ביטול בשלילה, בלי פועל ביטול משלו (למשל "לא רוצה לבטל את התביעה אלא את הפוליסה"), הכלי רק מסלים אם יש תביעה פתוחה; אחרת הוא מבקש מהנציג לברר במקום לתת הערכה. זו בחירה מכוונת: אף סכום לא ניתן על סמך ניחוש למה "אלא" מתייחס.
- **שונות של המודל:** סיווג הכוונה הוא הסתברותי. בהרצות יציבות מוקדמות יותר, `lang-exit` ("לא שילם ורוצה לצאת") נקרא כשאלת פרטי פוליסה ב-1 מתוך 5 הרצות – נתונים אמיתיים, בלי סכום, מסווג כהיפוך לא מזיק; בהרצה הסופית השמורה (`eval/stability_report.txt`) לא היו היפוכים. כלל השגיאה בבדיקת היציבות צומצם אחרי ההרצה החיה הזו, בדיוק מהסיבה הזו.
- **באג שנמצא בהרצה חיה ותוקן:** תשובות כלליות נקטעו, כי טוקני החשיבה של המודל נספרים בתוך `max_tokens`. הקריאה הכללית מקבלת עכשיו 4096 טוקנים ומגבלה של 120 מילה.
- **נתונים שאין בייצוא הפיילוט:** פרמיה ששולמה מראש, היסטוריית הקפאות, תביעות ששולמו ב-12 החודשים האחרונים, חוב שנצבר, שלב התביעה הנוכחי, תאריך היציאה בפועל לנסיעה. לכן כל הערכת ביטול מותנית ומפרטת מה חסר.
- **פרשנויות שמוצגות לנציג כהנחות:** גבולות מדרגות מענק הוותק (3 שנים בדיוק = 10%), תאריכי DD/MM, חודש חיוב = חודש קלנדרי, מועד הבקשה = תאריך השאלה, וביטול נסיעות לפני תחילת הכיסוי אינו תקופת התחרטות.
- **תשובות כלליות נבדקות למספרים ולציטוטים, לא למשמעות** – הנציג רואה את טקסט המקור המצוטט כדי לאמת. שאלה כללית יכולה לקחת עד כ-12 שניות במקרה הגרוע (timeout של 4 + 8 שניות).
- **מספרי פוליסה** מניחים 4 ספרות; 1900–2100 נקראים כשנים. `open_claims` מעל 1,000 נחשב לא תקין.
